# KANTAN GB PLAY — 技術レポート

ゲームボーイカラー用のコード演奏楽器ROM。MODRETRO ChromaticのカスタムFPGAビルド
（YM2151/OPMコア＋MSM6258系ADPCMチャンネル搭載）もターゲットにしています。
本書はROMの仕組みと設計判断の記録です。

## 1. アーキテクチャ

```
main.c        入力デバウンス、フリーラン8分音符グリッド、デモシーケンサ
chord.c       コードテーブル（KANTAN Music API実出力）、十字キー判定
sound.c       GB APUドライバ（フォールバック経路: 通常のGBC/エミュレータ）
ym2151.c      Chromatic拡張ドライバ（FF28-FF2F経由のOPM＋ADPCM）
ui.c          タイルUI、GBC属性ハイライト、ステータス表示
```

起動時に `FF2E` を読み、`0x51` ならYM2151/ADPCM経路、それ以外はGB APUへ
フォールバック。コードロジック・タイミング・UIは両経路で共通です。

## 2. コードエンジン

ボイシングはKANTAN Music APIの「実際の出力」です。`KANTAN_Play_core` には
プラットフォーム別のビルド済みライブラリが同梱されており、`m1mac` 版は
Apple Silicon上でそのまま動くため、小さなCハーネスから
`KANTANMusic_GetMidiNoteNumber()` を全degree/pitchで呼んで結果を
`chord.c` に落とし込みました（Closeボイシング、key=C、pitch 4-6）。

記録すべき発見：

- KANTANのdegree 7のデフォルトは **Bdimではなく Bm**（dimはモディファイア）
- `minor_swap` は長短を反転する。スワップ側テーブルも同じ方法でダンプ
- C7は degree 1 ＋ `Modifier_7`
- `bass_degree = 1`（オンコード）ではpitch 1が常にC、pitch 2はミュート
  — ROMが実装している「X/C ペダルベース」そのもの

APU経路はコードにパルス2声しか使えないため、テーブルは
`{補助音, ルート系, 3度系}` の順に並べ、**鳴らす2音に必ず3度を含む**ように
しています（そうしないとFとFmの違いが落ちる音に乗ってしまい区別不能）。

## 3. タイミング

起動時からフリーランする8分音符グリッドが1本：`8分あたりフレーム数 =
round(1800 / BPM)`（約60fps）。ベースの刻み・ドラム・コードのキーオフは
すべてこれにクォンタイズされます（キーオンは演奏性優先で即時。B単独
リリースではリトリガーしない）。グリッドはリセットされないため、Aを
押し直してもグルーヴは崩れません。ジョイパッドは2フレーム連続一致で
確定するデバウンス付きです。

## 4. GB APU経路

| チャンネル | 役割 |
|---|---|
| CH1/CH2（パルス） | コード（ルート＋3度のサブセット） |
| CH3（波形・三角波） | オクターブベース C2↔C3、Cペダル |
| CH4（ノイズ） | キック / スネア / ハット / クラッシュ |

周波数テーブルは `P = 2048 - 131072/f` でC2〜B7をカバー。CH3は同じ
周期値でパルスより1オクターブ低く鳴るため、ベースは `note + 12` で
テーブルを引いて補正します。ドラムはエンベローププログラム
（キック=最大音量から最速減衰の深い15bitノイズ、ハット=7bit LFSR＋
レングスカット、クラッシュ=遅い減衰）。

## 5. Chromatic拡張（FF28-FF2F）

| レジスタ | 機能 |
|---|---|
| FF28 | OPMレジスタアドレス。`0xFF`/`0xFE`/`0xFD` はADPCMエスケープ（データモード/再生/停止、直後のFF29書き込みでコミット） |
| FF29 | OPMデータ。データモード中はADPCMサンプルデータ |
| FF2A | bit7 YM/ブリッジbusy、bit6 ADPCM FIFO ready、bit5 ADPCM再生中 |
| FF2B | bit7-4 ADPCM音量、bit2 ADPCM有効、bit1 GB APU有効、bit0 YM有効 |
| FF2E | 拡張ID（`0x51`） |
| FF2F | 拡張バージョン（`0x03` = ステータス分離版） |

FF28の `0xFD-0xFF` がエスケープであるため、OPMレジスタ0xFD-0xFF
（ch5-7のC2スロットのD1L/RR）には書けません。よってそれらのチャンネルは
未使用とし、CH0-2=コード、CH3=FMハイハット、CH4=ベースの構成です。

OPMボイスはMDXの27バイトレイアウト（FL/CON、スロットマスク、以降
オペレータ毎に DT1/MUL・TL・KS/AR・AME/D1R・DT2/D2R・D1L/RR を
M1,M2,C1,C2順）を `0x40+i*8+ch` … `0xE0+i*8+ch` へ書き込みます
（mdxtoolsと同じレジスタ対応）。キーコード変換はOPM特有の
「1オクターブ12音を4bitコード（C#=0…C=14）に飛び飛びで割り付ける」方式で、
上下端はクランプ。

コードとベースのパッチはX68000スペースハリアーMDXカバーが使うOPM
ボイスパラメータ（シンセ設定値であり音声データではない）。FMハイハットは
フィードバック最大の1オペレータパッチで、自己変調によりサイン波が
金属的なヒスに化けることを利用しています。

## 6. ADPCMドラム

FPGA側は1chのMSM6258系デコーダ（OKI 4bit ADPCM、15.625kHz）＋
256バイトFIFO。GBのI/OにはDMAが無いためCPUがストリーミングします：
必要量は約131バイト/フレームで、ドライバはFF2A bit6（ready）を見ながら
毎フレーム最大160バイトを給送。給送前にbit7（ブリッジbusy）を待つことで、
JT51書き込みが飛行中の先頭バイトドロップを防ぎます。発音時はFIFOに
プライミング（停止→データモード→160バイト→再生）し、以降は
`ym_adpcm_tick()` が毎フレーム補充。CPUコストはフレームの10〜15%程度です。

コミットされているサンプルは自前合成のオリジナル
（`tools/gen_drums.py` → `tools/adpcm.py` のOKIエンコーダ、
デコーダに合わせて低ニブル先行）。`tools/pdx2c.py` でMDXのPDXから
スロットを抽出して**ローカル**テストに使えますが、抽出したゲーム音声を
コミットしてはいけません。

## 7. MDX解析

デモの進行・テンポ・リズムパターン・音色は、X68000スペースハリアー
メインテーマのMDXカバー群を自作Pythonパーサ（フォーマットはmdxtoolsの
ドキュメント準拠）で解析した結果です：ノートバイト `0x80+n` → MIDI `n+3`、
4分音符=48tick、テンポ `BPM = 4883 / (256 - @t)`。FMチャンネル全体の
発音中ピッチクラスを半小節ごとに集計すると、進行は
**C → F → Fm → C**（×3）＋ターンアラウンド **F → Dm → Fm → C**、
`@t225 ≒ 157.5 BPM` で、独立した3カバーで一致しました。リズムトラックは
4つ打ちキック＋8小節ごとのフィル、ベーストラックは8分のオクターブ交互。
進行・テンポ・リズムパターンは楽曲についての事実であり、メロディの
データは含みません。

## 8. UIパイプライン

ホイール（11×11タイル）と丸数字バッジは `tools/gen_wheel.py` /
`tools/gen_badges.py` が生成：1bitビットマップに描画→2bppのGBタイルに
分割→重複排除（ホイールはユニーク73タイル）→C配列＋タイルマップを出力。
VRAMはフォント0-95（GBDK stdio）、十字キー128-132、ホイール133-205、
バッジ206-212。ハイライトはGBC属性マップの書き換えのみ
（パレット1=選択、2=発音中）で、実行時にタイルは書き換えません。

## 9. 遭遇したGBDKの落とし穴

- `printf("%u", (uint8_t)x)` は化ける：可変長引数は昇格されず、`%u` は
  16bit読む。`uint16_t` へキャスト（症状：`OCT:-2` が `OCT:-512` 表示）
- `printf("%c%c", a, b)` は2文字目が落ちる。`%c` は1呼び出し1個で
  （症状：「Em」が「E」、HEXダンプの桁欠け）
- 行17の列19に書くとコンソールがスクロールし、行0が静かに消える
- 波形チャンネルは同じ周期値でパルスより1オクターブ低い。`+12` で補正
- フィールド幅（`%02X`）は無視される。HEXは手組みで整形
